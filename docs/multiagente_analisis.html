⚖️ Lex RAG → Multi-Agente

Análisis arquitectónico: costos, impacto en calidad y plan de implementación

1. Estado actual vs Multi-Agente

🔴 Hoy: Pipeline secuencial

  • 1 orquestador monolítico — run_console_query() ejecuta todo en serie
  • 2-3 LLM calls/consulta (router + síntesis + follow-ups)
  • Sin feedback loop — lo que sale del LLM va directo al usuario
  • top_k fijo — siempre 7 documentos, sin importar la complejidad
  • Sin verificación — si el LLM alucina una cita, nadie la detecta
  • 1 solo rol — el mismo LLM hace de juez, escritor y corrector

🟢 Multi-Agente: Pipeline orquestado

  • 1 orquestador + 4-5 agentes especializados
  • 5-8 LLM calls/consulta (cada agente aporta su llamada)
  • Feedback loop — el crítico puede pedir re-escritura o re-retrieval
  • top_k adaptativo — el retrieval strategist decide según la consulta
  • Verificación de citas — el crítico valida que cada cita exista en el corpus
  • Roles separados — cada agente tiene un prompt experto diferente

2. Los agentes propuestos

Agente Rol LLM calls Herramientas Complejidad
🔀 Router Clasifica consulta + genera HyDE + sugiere estrategia retrieval 1 Prompt + temperature=0.0 🔵 Baja (ya existe)
🎯 Retrieval Strategist Define plan de búsqueda: top_k dinámico, peso FAISS/BM25, fuentes 1 Prompt + accesso a metadatos del corpus 🟡 Media
🕸️ Graph Analyst Analiza NetworkX: frecuencias, patrones, cadenas de precedente 0-1 NetworkX API (algorítmico) + LLM para interpretación 🟡 Media
✍️ Legal Writer Redacta dictamen con estructura forense y citas 1 Prompt + contexto recuperado + historial 🔵 Baja (evolución del synthesizer)
🔍 Critic Verifica citas, detecta alucinaciones, evalúa calidad 1-2 Prompt + acceso a FAISS (verificar que un doc_id existe) 🔴 Alta (lógica de verificación)
🧠 Orchestrator Coordina flujo, decide iteraciones, consolida respuestas 0-1 Delegate a agentes, decide feedback loop 🔴 Alta

3. Análisis de costos

3.1 LLM calls por consulta

Escenario Calls actual Calls multi-agente Incremento
Consulta simple (LOCAL, respuesta directa) 2 5 (router + strategist + graph + writer + critic) 2.5×
Consulta compleja (estadística + feedback loop) 3 8 (router + strategist + graph + writer + critic + 1 re-write + follow-up) 2.7×
Consulta WEB (búsqueda externa) 2 5 (router + strategist + web search + writer + critic) 2.5×

3.2 Costo monetario estimado

Usando Groq (modelo base: llama-3.3-70b ~$0.59/M input tokens, $0.79/M output tokens via Groq — realmente Groq es gratis/rate-limited). Con DeepSeek V4 u otro proveedor pago:

Métrica Actual Multi-Agente
Input tokens promedio/query ~4,500 ~12,000 (cada agente recibe contexto relevante)
Output tokens promedio/query ~1,200 ~3,500 (múltiples agentes generan)
Costo/query (DeepSeek V4 flash) ~$0.002 ~$0.008
Costo/query (DeepSeek V4 pro) ~$0.015 ~$0.06
Costo batería 100 queries/día ~$0.20 ~$0.80
Costo mensual (3,000 queries) ~$6.00 ~$24.00

⚠️ Consideraciones de costo real

  • Groq es gratuito (con rate limits) — el costo adicional en LLM calls es cero mientras uses Groq. El incremento real está en latencia (más calls seriales).
  • DeepSeek / OpenAI — el costo 4× puede mitigarse usando modelos más baratos para agentes auxiliares (router, strategist, critic con modelos pequeños tipo llama-3.1-8b cuestan 10× menos).
  • El Critic Agent puede ejecutarse con un modelo 8B que cuesta ~$0.04/M tokens → ~$0.0005 por verificación.
  • Si el crítico detecta un problema y pide re-escritura, el costo se duplica en esa consulta pero ganas en calidad.

4. Impacto en la calidad de las respuestas

✅ Mejoras esperadas

  • Menos alucinaciones — el Critic verifica que cada CAS. N°/EXP. N° exista realmente en el corpus. Si el Writer inventó una cita, el Critic la detecta y pide re-escritura.
  • Mejor estructura — el Writer puede especializarse en un formato específico (tablas, secciones, citas formales) sin que el Router tenga que preocuparse por eso.
  • Recuperación adaptativa — el Strategist puede pedir más chunks si la consulta es compleja, o menos si es simple. Hoy siempre top_k=7.
  • Análisis estadístico real — el Graph Analyst puede contar frecuencias con precisión algorítmica en vez de depender de que el LLM "adivine" cuántos casos hay.
  • Repreguntas contextuales — el historial multi-agente permite que el Writer recuerde qué dijo en la consulta anterior con precisión.
  • Trazabilidad multi-nivel — cada agente puede dejar su propio audit trail, no solo los chunks sino también las decisiones de cada agente.

⚠️ Riesgos y desventajas

  • Latencia mayor — 15-28s vs 12-18s. En modo interactivo se nota. El streaming ayuda a disimularlo.
  • Complejidad de debugging — 6 agentes = 6 veces más puntos de fallo. Si el Critic rechaza una respuesta válida, hay que debuggear por qué.
  • Overhead de tokens — cada agente recibe contexto (instrucciones, historial) que se suma al total. Aunque los agentes auxiliares usen modelos más baratos, el input total crece.
  • Riesgo de loops infinitos — el Critic podría rechazar repetidamente. Necesita un límite duro (máx 2 iteraciones).
  • Calidad inconsistente entre agentes — si el Router funciona mal, todo el pipeline se degrada. Si el Critic es demasiado estricto, rechaza respuestas válidas.
  • Más código, más mantenimiento — cada agente es una clase con su prompt, tools, lógica. El código base crece 3-4×.

5. Plan de implementación por fases

Fase Qué incluye Esfuerzo Riesgo Valor
Fase 1 Critic Agent — añadir verificador de citas POST-síntesis. Lee la respuesta, verifica que cada doc_id exista en FAISS. Si encuentra una cita inventada, marca advertencia. Sin re-escritura automática. 🟢 1-2 días 🟢 Bajo 🔥 Alto (detecta alucinaciones)
Fase 2 Retrieval Strategist — antes de recuperar, el strategist analiza la query y decide top_k y pesos. top_k dinámico (3-15) en vez de fijo 7. 🟡 2-3 días 🟡 Medio 🔥 Alto (recuperación adaptativa)
Fase 3 Graph Analyst Agent — agente especializado en consultas estadísticas. Ej: "qué juez emitió más sentencias" → usa NetworkX algorítmicamente + LLM para narrativa. 🟡 2-3 días 🟡 Medio 🔥 Alto (precision estadística)
Fase 4 Feedback loop — cuando el Critic detecta un problema, el Orchestrador decide si re-escribir o re-recuperar. Máx 2 iteraciones. Sistema de scoring de calidad. 🔴 3-5 días 🔴 Alto 💎 Máximo
Fase 5 Orquestador formal — refactorizar run_console_query() como un Orchestrator Agent que delega explícitamente. Cada agente es una clase con `async def run()`. 🔴 3-5 días 🔴 Alto 💎 Máximo

Recomendación: Fase 1 ya

El Critic Agent es el de mayor valor con menor riesgo. No cambia el pipeline existente — se ejecuta después del Writer y solo emite una advertencia si detecta una cita falsa. En una segunda iteración, puede pedir re-escritura. Es implementable en 1-2 días y resuelve el problema más grave de cualquier RAG: las alucinaciones en citas jurisprudenciales.

Ejemplo de firma de agente (Python)

class CriticAgent:
    """Verifica que la respuesta del Writer use citas reales del corpus."""

    def __init__(self, llm_client, faiss_index, metadata):
        self.llm = llm_client
        self.faiss = faiss_index
        self.metadata = metadata

    async def verify(self, response: str, context_docs: list) -> Verdict:
        # 1. Extraer todas las citas (CAS. N°, EXP. N°, doc_id) de la respuesta
        cited_docs = extract_citations(response)

        # 2. Verificar que cada doc_id existe en FAISS/metadata
        missing = [d for d in cited_docs if d not in self.metadata]

        # 3. Verificar que cada cita está realmente en el contexto entregado
        hallucinated = [d for d in cited_docs if d not in context_docs]

        # 4. LLM evalúa coherencia general (opcional)
        if hallucinated:
            return Verdict(
                passed=False,
                errors=[f"Cita inventada: {d}" for d in hallucinated],
                action="re-rewrite"  # o "warn-only" en Fase 1
            )

        return Verdict(passed=True, errors=[], action="accept")

7. ¿Vale la pena?

👍
CUANDO SÍ
  • El sistema se usa profesionalmente (abogados reales confiando en las respuestas)
  • Las alucinaciones en citas tienen costo real (mal praxis, demandas)
  • Necesitas consultas estadísticas precisas ("cuántos casos", "qué juez")
  • Tienes presupuesto para ~$20-30/mes en LLM o usas Groq gratuito
🤷
ZONA GRIS
  • Uso personal / exploratorio
  • Las consultas son siempre del mismo tipo (ej. solo laboral simple)
  • Estás OK con una tasa baja de alucinaciones
  • No necesitas consultas estadísticas
👎
CUANDO NO
  • La latencia es crítica (necesitas respuestas en <10s)
  • Estás en la fase de prototipo/validación (primero funcione, luego mejore)
  • El corpus cambia semanalmente (mantener agentes actualizados es overhead)
  • Tienes recursos limitados de desarrollo

🎯 Mi recomendación

Implementa solo el Critic Agent (Fase 1) ahora. Es bajo riesgo, bajo esfuerzo (1-2 días), y resuelve el problema más urgente: verificar que las citas jurisprudenciales sean reales. El resto del pipeline multi-agente puede esperar a que valides si el Critic mejora la calidad percibida. Si después del Critic ves que las consultas estadísticas son inexactas, añade el Graph Analyst (Fase 3). Si el retrieval es insuficiente para consultas complejas, añade el Strategist (Fase 2). No necesitas todo o nada. Cada agente es incremental. Empieza por el que más valor da con menos riesgo.
